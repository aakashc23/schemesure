# Design decisions

Every non-obvious choice made while building SchemeSure, why it was made, what
else was considered, and what it costs. Decisions backed by a measurement say so
and give the number.

---

## 1. Environment and stack

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **Python 3.12.4 instead of 3.11** | 3.12 was the only interpreter installed on the build machine, and every pinned dependency supports it. | Install 3.11 alongside; use pyenv. | None in practice. The Dockerfile pins `python:3.12-slim`, so local and deployed runtimes match — which matters more than the exact minor version. |
| **LLM `qwen/qwen3.8-27b`** | Chosen by probing the live account, not from a spec sheet. Only `gpt-oss-*`, `qwen` and some audio/guard models were available — `llama-3.3-70b-versatile` and `llama-3.1-8b-instant` both return **404**. The `gpt-oss` models are *reasoning* models: they spend completion tokens on hidden reasoning before emitting content, so `max_tokens=256` returned **empty content** and a `json_validate_failed` error. `qwen3.8-27b` uses **zero** reasoning tokens, was fastest (360 ms vs 811/860 ms on the same prompt), scored **5/5** on a judge probe including rejecting plausible-but-unstated claims, answers correctly in English/Devanagari/Hinglish, and was the **only** candidate to label Hinglish correctly. | `openai/gpt-oss-120b` (works at default reasoning effort, 3× the output tokens); `openai/gpt-oss-20b` (same reasoning overhead); `reasoning_effort=low` on gpt-oss — rejected because it broke the task: the normalizer stopped translating and echoed the Hinglish query back unchanged. | A 27B model is less capable than a 120B one in the abstract. Mitigated by the judge probe and by the guardrail's Python layer, which does not depend on model quality. Also emits 2.6× fewer output tokens than gpt-oss-20b, which matters against an 8,000 tokens/minute budget. One `.env` line to change. |
| **Guard against empty model content** | A reasoning model returning `""` on an HTTP 200 surfaced downstream as an unexplained JSON parse failure. The client now raises immediately and names the cause. | Let it fail at the parse step. | One extra check per call. Turns a 20-minute debugging session into a one-line error message. |
| **Retries parse the server's own wait hint** | Groq's free tier enforces a rolling **8,000 tokens/minute** budget (identical across every model on this account) and its 429 body states exactly how long to wait: *"Please try again in 1.68s"*. Fixed exponential backoff (2s/4s/8s) either slept far longer than necessary or retried too early and burned an attempt — which is what made a judge call exhaust its retries and fail-close to BLOCK on a question that should have passed. | Fixed exponential backoff; a fixed long sleep; raising the retry count alone. | A little parsing of an error string, which could change format. Falls back to exponential backoff when no hint is present, and retries were raised 3 → 5. |
| **`openai` client pointed at Groq** | Groq implements the OpenAI wire format, so only `base_url` changes. Switching providers later means editing `.env`, not code. | Groq's own SDK; raw `requests`. | None. |
| **SQLite for the call log** | Zero setup, ships inside the container, and "how many tokens did this cost?" becomes one `SELECT`. `/metrics` reads real measurements that survive a restart. | In-memory counters (lost on restart); Prometheus (another service to run). | Not suited to many concurrent writers. Fine here: one container, low traffic, and writes are wrapped in a lock. |
| **`temperature=0.0` everywhere** | This is an extraction, judging and grounded-summarisation system, not a creative one. The same evidence must produce the same answer, and the same claim must get the same verdict. | Higher temperature for a more natural tone. | Slightly flatter prose, in exchange for reproducibility — essential when evaluating whether the guardrail changed anything. |

## 2. Scheme data

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **Read the myScheme JSON API rather than scrape the HTML** | `myscheme.gov.in` is a JavaScript single-page app: fetching a scheme page returns an empty shell with no scheme content. The page is rendered from a public JSON API on the same official domain (`/api/apisetu/schemes?slug=...`), which returns the editors' own markdown in `*_md` fields. | Render each page in a headless browser (slow, brittle); hand-copy facts (error-prone, unverifiable). | Depends on an endpoint that is public but undocumented. Mitigated by keeping every raw response in `data/raw/`, so the corpus can be rebuilt or audited even if the API changes. |
| **One source for all 15 schemes** | Identical structure across schemes means one parser, one set of section names, and consistent chunking — and all 15 carry the same provenance guarantee. | Pull each scheme from its own ministry portal. | Less redundancy: an error on myScheme propagates to us. Mitigated by `reference_urls` (the scheme's own guideline PDFs) in every file and by `docs/VERIFY_CHECKLIST.md` for human spot-checks. |
| **Skipped Ayushman Bharat PM-JAY and Sukanya Samriddhi Yojana** | Both were named as examples in the brief, but neither is present as a central scheme on myScheme (PM-JAY appears only as state variants; Sukanya returns no results), and `nha.gov.in/PM-JAY` served an empty page. The brief's rule is explicit: if no official page works, skip it and pick another. | Fill the gap from memory. | Two very well-known schemes are missing, so a user asking about them gets a refusal. This is the correct behaviour — and it became a deliberate test case in the golden set. Substitutes: PMFBY, Kisan Credit Card, PM Vishwakarma, PMMVY, PMKVY. |
| **`"Not specified in official source"` instead of filling gaps** | The whole project is about not inventing facts. A visible gap is information; a plausible invention is a bug that is nearly impossible to spot later. | Omit empty sections; infer from related schemes. | Some sections read as sparse (4 schemes have no Exclusions, 2 no Documents Required). That sparseness is accurate. |
| **Normalised stray punctuation in reference URLs** | One official payload contains `": https://pmmvy.wcd.gov.in/..."` with a leading colon, which makes the link dead. Trimming it is a formatting fix, not a change of fact. | Leave it exactly as received. | A tiny divergence from the raw payload. The untouched original stays in `data/raw/`. |
| **Decoded HTML entities, twice** | Some fields arrive escaped and a few double-escaped (`&amp;#39;` → `&#39;` → `'`). Left alone, entity text reaches the LLM as evidence and can be echoed into answers. | Single-pass unescape. | None; `validate_data.py` fails the build if any entity survives. |

## 3. Retrieval

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **Embedding model: `paraphrase-multilingual-MiniLM-L12-v2`** | Chosen on measured separation, not reputation. Against the same correct passage: on-topic English **0.52**, off-topic **−0.08**. `intfloat/multilingual-e5-small` compressed everything into a narrow band — off-topic "capital of France" scored **0.70** against an on-topic **0.81**, and a question about a scheme we do *not* index also scored **0.80**. A threshold needs a gap to sit in, and e5 has none. | `multilingual-e5-small` (512 tokens, worse separation); `multilingual-mpnet-base-v2` (3× larger, same 128-token limit); `BAAI/bge-m3` (far better context, ~2.2 GB — too big for a free Space). | A 128-token input limit, which forces small chunks (see below). Accepted deliberately: usable thresholds matter more than long chunks, and small chunks make claim-level citation *more* precise. |
| **Chunk budget of 110 tokens, measured with the model's own tokenizer** | The model silently truncates at 128 tokens. A chunk over the limit looks indexed but is partly unsearchable — a bug that shows up as "retrieval is mysteriously bad". Measuring in tokens (not characters) makes it impossible. 110 leaves headroom for the header prefix. | Fixed character windows; ignore the limit. | More chunks (312 across 15 schemes) and some split context. `core/ingest.py` asserts zero chunks over budget and the test suite re-checks it with the real tokenizer. |
| **Section-aware chunking, split further at list-item granularity** | Documents already have meaningful boundaries (`## Benefits`, `## Eligibility`), so every chunk belongs to exactly one scheme and one section — which is what makes "PM-KISAN, Benefits" a real citation. Eligibility sections are mostly bullet lists, and one bullet is usually one checkable fact. | Fixed-size sliding window with overlap. | Slightly uneven chunk sizes. Worth it: a window would merge two schemes' rules into one chunk and make citations meaningless. |
| **List markers normalised to `-`** | The official API numbers *every* ordered item `1.`, so preserving markers packs chunks reading "1. x 1. y 1. z", which reads like a transcription error to both a model and a human. | Keep the original markers; strip them entirely. | Loses original numbering, which carried no information anyway. The bullet is kept so list structure survives. |
| **Readable deterministic chunk ids (`pm_kisan#benefits#0`)** | Re-running ingestion upserts rather than duplicates. More importantly, these ids are what the guardrail judge must cite, so a fabricated one is obvious at a glance and trivial to verify in code. | Content hashes (stable but opaque); UUIDs (not reproducible). | An id changes if a section is renamed. Acceptable: the index is rebuilt from scratch at every Docker build. |
| **`hnsw:space=cosine` set explicitly on the collection** | Chroma defaults to squared L2. With that default, the similarity threshold in `config.py` would compare against a number on a different scale and silently mean nothing. | Accept the default and convert. | None. Embeddings are normalised, so `score = 1 − distance` is exactly cosine similarity. |
| **`RETRIEVAL_MIN_SCORE = 0.45`** | Calibrated against 22 real queries, not guessed. Answerable English questions scored **0.574 – 0.893**; out-of-scope questions scored **0.100 – 0.350**. That leaves a safe window of 0.350 – 0.574, and 0.45 sits near its midpoint: ~0.10 above the worst off-topic case and ~0.12 below the weakest real question. | 0.35 (the initial guess — too permissive); 0.55 (would refuse the weakest genuine questions). | A genuine question phrased very unusually may fall under the line and be refused. Preferred to the opposite error, and the threshold is one `.env` line. |
| **Normalise the query to English *before* retrieving** | Measured, and the reason this step is not optional. The same PM-KISAN question: English **0.574** (correct scheme), Devanagari Hindi **0.610** (*wrong* scheme), romanised Hinglish **0.436** (*wrong* scheme — and below the 0.45 threshold). Without normalisation, a Hinglish speaker would be told we have no information about a scheme we have fully indexed. | Rely on the multilingual model directly; translate with a dictionary. | One extra LLM call per question (~25% of the per-question cost) and one more failure point. Mitigated: on failure it falls back to the raw query plus a script-based language guess and sets `fallback_used=True`, so degradation is visible rather than silent. |

## 4. Generation and the guardrail

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **Refuse before generating when evidence is weak** | If the best chunk is below threshold there is nothing to ground an answer in, so the model would simply write something plausible. Refusing here is safer *and* free. | Always generate, then rely on the guardrail. | A borderline question gets a refusal rather than a hedged answer. In exchange, out-of-scope questions cost **0 LLM calls**. |
| **Split answers into atomic claims before judging** | One sentence often carries two facts ("Rs 6,000 a year, paid in three instalments"). A sentence-level check passes the whole sentence if either half is right, which is exactly how a wrong number survives verification. | Judge the answer as a whole (cheaper, much blunter); judge sentence by sentence. | One extra LLM call. It is what makes the verdict mean something. |
| **The judge sees only the evidence, never the question** | A judge that knows what the answer was *supposed* to say is biased toward approving it. Withholding the question keeps the check adversarial. | Give the judge full context. | Occasionally the judge cannot tell that a claim is relevant. Harmless: irrelevant-but-supported claims are still removed by the repair step. |
| **"Probably true" counts as NOT_SUPPORTED** | The judge is instructed to ignore its own knowledge of these schemes. A real-world-correct fact that the passages do not state is still ungrounded, and allowing it reopens exactly the hole the guardrail exists to close. | Allow world knowledge when it agrees with the passages. | Higher over-blocking. Deliberate asymmetry: a wrongly withheld answer costs the user one web search, a wrongly confident one can cost them a wasted trip to a government office. Measured in `eval/results.md`. |
| **Citation validity is checked in Python, not by an LLM** | The judge can mark a claim SUPPORTED while citing a chunk id that was never in the evidence — an authoritative-looking verdict that is worthless. Set membership is something code gets exactly right, every time. | Trust the judge; ask a second LLM to check. | None. This is the cheapest and strictest check in the system, and `tests/test_guardrail.py` shows it turning a naive PASS into a correct BLOCK. |
| **The decision policy is a pure function** | `decide()` takes verdicts and a threshold and returns a decision — no I/O, no LLM. That makes the one piece that must not be wrong exhaustively testable with fabricated verdicts, including every boundary. | Fold the decision into the LLM prompt. | None. 20+ tests run in milliseconds and pin the exact boundaries. |
| **`ratio > threshold` blocks; exactly at the threshold repairs** | Matches the brief's ">50% unsupported → BLOCK". Safe at the boundary because REPAIR rebuilds from supported claims only, so a failing claim cannot survive either way. | `>=` (stricter). | At 50% unsupported the user gets a thinner answer rather than a refusal. |
| **Zero supported claims always blocks, whatever the threshold** | REPAIR would have nothing true to say and would emit an empty or invented answer. Checked before the threshold so a misconfigured value cannot produce one. | Rely on the threshold alone. | None. |
| **REPAIR regenerates from the verified claims only** | Not "ask the model to try again" — it is handed a fixed list of verified facts and told to state those and nothing else, so the claim that just failed cannot reappear. | Delete the offending sentences textually (leaves incoherent prose); re-run generation with a sterner prompt (can reintroduce the same error). | One extra LLM call, and the repaired answer is terser. |
| **Fail closed: if verification cannot run, refuse** | If the splitter or judge call fails we have an unverified draft and no way to check it. Shipping it would mean the guardrail silently stops protecting the user exactly when the LLM is misbehaving. | Ship the unverified draft; retry indefinitely. | Availability is traded for safety — a Groq outage produces refusals rather than unchecked answers. The right trade for benefit information, and every such refusal is logged with its reason. |
| **Refusal messages are hand-written constants in all three languages** | A refusal is the one message that must never itself be hallucinated — and we often refuse precisely because the LLM cannot be trusted on this input. Asking it to phrase the refusal is circular. | Generate refusals with the LLM. | Fixed wording, less conversational. Also free and instant. |
| **One judge call for all claims, not one per claim** | Keeps the cost of a question at a predictable 4 LLM calls (5 with repair) and lets the judge see the whole evidence block once. | One call per claim (more focused, 3–4× the cost and latency). | A judge handling many claims at once can get sloppy or drop entries. Mitigated: verdicts are realigned by position and then by claim text, and any claim left without a verdict **fails closed** to NOT_SUPPORTED. |
| **A separate `UNVERIFIED` answer status** | The evaluation runs with the guardrail off as a baseline. Labelling those answers "verified" would be a lie in the one place the whole project is being measured. | Reuse `VERIFIED`; reuse `PARTIALLY_VERIFIED`. | One extra enum value. |

## 5. Eligibility

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **The LLM extracts; Python decides** | Eligibility is arithmetic and set membership. Code is exactly right every time; an LLM is approximately right most of the time. It also has to be auditable — "your age 35 is above the maximum of 25" is a reason a person can dispute, "the model said no" is not. | Ask the LLM for the verdict; fine-tune a classifier. | The engine only knows rules someone encoded. Accepted: the alternative is unverifiable advice about other people's money. |
| **Three-valued result, with `NEED_MORE_INFO`** | If a scheme has an income cap and the user never mentioned income, the honest answer is a question, not a guess. Missing data is not a default. | Assume the best case (over-promises); assume the worst (hides entitlements). | Users must supply more detail for a definite answer. That is the correct ask. |
| **A definite failure outranks missing information** | Age 15 against a minimum of 18 is decisive even with income unknown. Reporting NEED_MORE_INFO there would send someone to collect documents for a scheme they cannot have. | Report NEED_MORE_INFO whenever anything is missing. | None. |
| **Unstated fields stay `None`, never inferred** | A guessed value produces a confidently wrong verdict. Covered by a test: "farmer" must not imply male, so a women-only scheme reports NEED_MORE_INFO rather than NOT_ELIGIBLE — guessing would hide a scheme a woman is entitled to. | Infer gender from occupation or name. | More NEED_MORE_INFO results. |
| **A flat 7-field schema plus `unmodelled_conditions`** | Some official conditions genuinely do not fit numeric fields: Stand-Up India's "if the applicant is male, he must be SC/ST" is conditional, and PM Ujjwala's categories are *alternatives*, not requirements. Forcing those into `gender`/`category` would produce confidently wrong filters. | A general rule DSL (much more complex); drop what does not fit (silently wrong). | ELIGIBLE means "passes every rule we can mechanically check", never a guarantee — so the unmodelled conditions are always shown alongside the verdict. |
| **Every encoded rule cites its official sentence** | A number with no sentence behind it is an unverifiable claim. `rule_sources` puts the provenance next to the rule, `validate_data.py` fails the build if any active rule lacks it, and `VERIFY_CHECKLIST.md` prints both side by side. | Store rules bare. | More verbose rules files. This is what makes the data auditable at all. |
| **`min_age: 18` for PM Ujjwala from "an adult woman"** | The source says "adult", not a number. 18 is the statutory age of adulthood in India. It is flagged as derived in `rule_sources` rather than presented as quoted text. | Leave `min_age` null (loses a real restriction); treat it as quoted (overstates the source). | The one rule in the set that is an interpretation rather than a quotation. Called out explicitly so a reviewer can disagree. |
| **PMAY-U income cap = ₹18,00,000** | The scheme defines four income bands (EWS / LIG / MIG-1 / MIG-2); ₹18,00,000 is the top of the highest. The engine checks only the overall ceiling and records that band selection is not modelled. | Encode all four bands (needs a richer schema). | Someone earning ₹5,00,000 is told they pass the ceiling, not which vertical applies. Noted in `unmodelled_conditions`. |

## 6. Repository and build hygiene

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **`.gitignore` with `.env` written before `git init`** | A secret committed to a public repo is leaked permanently — rewriting history does not un-publish it. The only reliable fix is never committing it. | Add it later. | None. |
| **`scripts/scan_secrets.py` run before every push** | Defence in depth behind `.gitignore`: it scans exactly the content git is about to send, checks `.env` is untracked and that `.gitignore` still lists it, and redacts any match it reports so a secret is never printed. | Rely on `.gitignore`; use a hosted scanner. | Occasional false positives, filtered by a placeholder heuristic. Seconds of noise versus a rotated account. |
| **`.gitattributes` forcing LF on `*.sh`** | Built on Windows, run in a Linux container. A CRLF `start.sh` fails with a baffling "no such file or directory" because the `\r` becomes part of the interpreter path. Fixed before it could happen rather than debugged later. | Convert at build time in the Dockerfile. | None. |
| **Raw API responses committed to `data/raw/`** | Makes "every fact traceable to a response we actually received" checkable by anyone reading the repo, not just a claim in a README. | Keep only the processed markdown. | ~400 KB of JSON in the repo. Cheap for a verifiable audit trail. |
| **Explicit UTF-8 on every file read and write** | Windows defaults to cp1252, which cannot represent Devanagari or the rupee sign and throws on the first Hindi character. Hit this immediately while inspecting the API payloads. | Rely on platform defaults. | None. Worth knowing as a portability trap. |
| **Scheme data generated by scripts, not hand-edited** | `fetch_schemes.py` → `build_rules.py` → `validate_data.py` → `make_verify_checklist.py` is a reproducible pipeline. Refreshing the corpus is one command, and the rule-translation table sits in one reviewable file beside the official sentences. | Hand-write the markdown and JSON. | An extra layer to understand. It is what makes the data auditable and re-runnable. |

## 7. Deployment (revised mid-project)

The project was built for a Hugging Face Docker Space. Deploying revealed that
this is no longer possible on a free account, so this section records what
changed and why.

| Decision | Why | Alternatives | Trade-off |
|---|---|---|---|
| **Live demo on Streamlit Community Cloud instead of a Hugging Face Space** | `create_repo` returned **402 Payment Required**: *"Static Spaces are free for everyone, but hosting Gradio and Docker Spaces on free cpu-basic requires a PRO subscription."* Probing every SDK confirmed only `static` is free, and the `streamlit` SDK no longer exists at all (the API accepts only `gradio`, `docker`, `static`). A static Space cannot run Python, so **no** free HF Space can host this. Streamlit Community Cloud is free, needs no payment method, and redeploys on every push. | HF PRO ($9/month — zero changes needed); Google Cloud Run (runs the Dockerfile unchanged, free within limits, but requires a card and has 30–60s cold starts); Render / Fly.io — both ruled out by measurement, since the app uses **~1.2 GB RSS** (almost all torch) against their 512 MB free ceilings. | The live demo is not the Docker container. The container remains the production path and still runs locally, on Cloud Run, or on a PRO Space. The user chose this option after being shown all three. |
| **FastAPI runs in a background thread rather than merging the UI and core** | Streamlit Cloud gives you exactly one process. The cheap fix is to have the UI import `core/` directly — but then business logic lives in the UI, and the evaluation harness would measure a different code path from the one users hit. Starting the real FastAPI app in a daemon thread keeps the HTTP boundary intact: the UI still only makes HTTP calls, all logic stays behind the API, and the eval still measures the same pipeline. | Merge the UI and core (loses the boundary); run FastAPI as a subprocess (Streamlit re-runs its script on every interaction, so a subprocess would be orphaned or re-spawned). | One process serving both, so they share a memory limit and a crash takes both down. Verified working: the thread-based API answers `/health` in ~9s with all 312 chunks loaded. |
| **The app builds its own index at startup if one is missing** | The Docker image builds the index at build time, so this is a no-op there. But Streamlit Cloud has no build step, and an empty index means every question is refused — a failure that looks like a model problem rather than a missing build step. | Commit `chroma_db/` to git (binary, goes stale silently, bloats the repo); require a manual step (will be forgotten). | ~25s added to a cold start, once. Measured: empty directory → 312 chunks in 23.2s. |
| **CPU-only torch pinned in `requirements.txt`, not just the Dockerfile** | Hosts without a build step install from `requirements.txt` and nothing else. PyPI's default Linux `torch` wheel is the CUDA build at ~2.5 GB, which wastes the download entirely on a GPU-less host and can exhaust a free tier's disk or build timeout. | Leave torch to the Dockerfile only (breaks Streamlit Cloud); install the CUDA wheel anyway. | Needs platform markers, because Windows has no `+cpu` build published while its default PyPI wheel is already CPU-only. |
| **The HF deploy job is manual-only (`workflow_dispatch`)** | On a free account it returns 402. A job that fails on every single push trains everyone to ignore a red tick, which defeats the point of having CI at all. | Delete the job (loses the path for PRO users and Cloud Run); leave it failing. | The normal deploy path is not gated on CI — Streamlit Cloud rebuilds on push regardless of whether tests passed. The gate that does hold is that tests run on every pull request. Stated plainly in `docs/DEPLOYMENT.md` rather than implied to be stricter than it is. |
| **CI builds and smoke-tests the container** | Docker is not installed on the build machine, so the Dockerfile was an untested claim — and it is the one artifact unit tests cannot cover, being where the build-time index build, the CPU-torch install and the two-process startup converge. CI builds the image, starts it, waits for Streamlit, then execs inside to confirm the internal API reports 15 schemes and a populated index. | Trust the Dockerfile; test it manually once. | ~10 minutes of CI time per push. Free on a public repo, and it verifies the deployment artifact on every change. |
| **The HF Space README front-matter is generated at upload time** | A Space is configured by YAML front-matter at the top of its README. Keeping that block in the repo's own README makes GitHub render a stray table above the project title. | Keep the front-matter in the repo README; maintain two README files. | `deploy_hf.py` has to prepend it, and uploads the README separately. |
| **Uploads use an allow-list, not an ignore-list** | A deny-list fails silently the day someone adds a file that should not be published — and on a public Space, publishing a secret is irreversible. With an allow-list, a new file is simply not uploaded until someone adds it: failing in the safe direction. | `ignore_patterns` (the more common approach). | New files must be added to the list deliberately. The script also refuses outright if `.env` or any database file matches. |

### What this cost, honestly

Phase 9 as specified is not achievable on a free Hugging Face account any more.
The container, the deploy script and the CI job for it are all written and
working; what changed is where the public demo is served from. The architecture
was kept portable precisely so that this was a deployment change rather than a
rewrite — which is the actual lesson worth taking from it.
